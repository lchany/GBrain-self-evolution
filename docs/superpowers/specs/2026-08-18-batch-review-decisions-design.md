# GBrain 批量审核决策设计

## 目标

在现有单条分类审核之外，为 inbox 列表增加最小化的批量操作。审核者勾选多条草稿后，只能做两种决定：

- **同意**：每条草稿分别采用它自己的模型推荐分类。
- **拒绝并删除**：每条草稿归类为 `reject`，写入审核记录后软删除。

界面不增加批量分类下拉框、目标选择、预检、确认短语或内部执行计划。现有单条审核继续允许审核者修改推荐分类。

## 已确认事实

- 当前审核列表展示模型推荐，单条详情页允许确认或修改最终分类。
- 模型推荐可能来自草稿中的 `review_recommendation`，也可能来自与草稿内容哈希绑定的进程内缓存。
- 分类提交由服务端重新读取草稿并生成内部 action；浏览器不能指定目标 slug、action、writer 凭据或确认字段。
- `reject` 的既有安全顺序是先写审核记录，再软删除草稿。
- 用户接受部分成功语义：成功项继续完成，失败项留在 inbox，不因单项失败回滚整个批次。

## 用户界面

审核列表增加：

1. 每行一个复选框。
2. 表头一个“全选当前页”复选框。
3. 已选择数量。
4. “同意”按钮。
5. “拒绝并删除”按钮。

未选择草稿时两个按钮禁用。批量请求执行期间禁用复选框和按钮，防止重复提交。完成后刷新列表：成功项消失，失败项继续显示，并展示成功数、失败数以及失败草稿的浏览器安全原因。

“同意”不显示也不提交统一分类。每条草稿仍按自己的模型建议处理。“拒绝并删除”不要求输入确认短语，也不跳转到预检页面。

全选只作用于当前页面已经加载的 inbox 行，不隐式选择未展示的草稿。

## 接口契约

新增管理员写入口：

```text
POST /admin/api/review/classify-batch
```

请求体只允许：

```json
{
  "sourceSlugs": ["inbox/example-a", "inbox/example-b"],
  "decision": "accept"
}
```

其中：

- `decision` 只能是 `accept` 或 `reject`。
- `sourceSlugs` 必须是非空数组，最多 50 项。
- 每项必须是合法的 inbox source slug。
- 服务端按首次出现顺序去重。
- 出现未知字段、未知 decision、空数组、超限或非法 slug 时，整个请求返回 400，且不开始写入。
- 路由继续要求管理员身份和严格同源校验。

响应按输入顺序返回每项结果，并只包含浏览器安全字段：

```json
{
  "ok": true,
  "succeeded": 1,
  "failed": 1,
  "results": [
    {
      "sourceSlug": "inbox/example-a",
      "status": "succeeded",
      "category": "runbook"
    },
    {
      "sourceSlug": "inbox/example-b",
      "status": "failed",
      "code": "recommendation_missing",
      "message": "该草稿缺少有效的模型推荐，已保留在收件箱。"
    }
  ]
}
```

批次已被合法接收并完成逐项处理时返回 200，即使部分或全部项目失败。请求级校验失败、管理员认证失败或同源检查失败使用现有 4xx 语义。

## 服务端处理

### 同意

对每个去重后的 source slug 顺序执行：

1. 重新读取最新草稿，避免使用列表加载时的过期内容。
2. 校验草稿仍位于 inbox 且可审核。
3. 从草稿中的有效 `review_recommendation` 或与最新内容哈希匹配的缓存中取得推荐。
4. 不接受浏览器提供的分类，也不使用列表中旧的显示值。
5. 将推荐分类转换为现有内部 action 和目标。
6. 运行现有 review core 门禁、写入、检索验证和审计流程。

推荐缺失、失效或模型缓存与最新内容不匹配时，该项失败并留在 inbox。批量入口不为缺少推荐的旧草稿临时调用模型，以避免一次批量点击产生不可控费用和长时间阻塞；审核者可先进入单条页面生成推荐。

如果推荐分类本身为 `reject`，“同意”表示接受该模型建议，因此该项执行既有拒绝流程并软删除。

### 拒绝并删除

对每个 source slug 强制使用最终分类 `reject`，无需模型推荐。服务端仍重新读取草稿，运行既有拒绝门禁，并保持“审核记录成功写入后才软删除”的顺序。

### 会话与失败隔离

一个批次建立一个经过 `whoami` 来源证明的内部 writer 会话，并顺序处理所有项目。逻辑门禁失败只影响当前项目，后续项目继续处理。

不得在写入结果不确定时自动切换 bearer/OAuth 或重试整个项目，以免产生重复写入。writer 传输故障后，当前项返回固定失败；若会话已不可用，剩余项目也返回固定写入失败并保留草稿。已成功项目不回滚。

## 错误与日志

- 每项失败使用受限错误码映射为固定中文提示，不向浏览器返回异常 message、stack、URL、Token 或正文。
- 服务端沿用 `logReviewFailure(stage, error)`，批量日志只记录固定 stage、受限 `Error.name` 和非敏感计数。
- 不把 source slug、草稿标题或正文写入错误日志。
- 页面仅展示失败草稿在列表中的安全名称、固定原因和汇总数量。
- 网络超时或浏览器中断后，不自动重放整个批次；用户刷新列表，以服务端最新状态为准后重新选择剩余项。

## 安全与维护约束

- 单批最多 50 项，顺序执行，避免并发写入造成重复、竞态或 writer 压力峰值。
- 严格拒绝请求体中的 `category`、`targetSlug`、`action`、`writer`、`confirmation` 等额外字段。
- 继续使用 Basic Auth、固定 Admin Origin、same-origin 检查、loopback writer URL 校验和同一来源 attestation。
- 每条草稿执行时重新计算项目绑定与目标，不信任浏览器状态。
- `review_recommendation` 只作为当次建议，不复制到最终页面；审核记录写最终 `review_category`。
- 保留现有单条 classify、plan/confirm 兼容接口；本次不扩大 API 删除范围。
- 不修改 review core 的门禁语义，也不改变匿名 MCP 的权限契约。

## 测试

### 接口校验

- 只接受 `sourceSlugs` 和 `decision`。
- 拒绝空数组、超过 50 项、非法 slug、未知 decision 和未知字段。
- 重复 slug 只处理一次，并保持首次出现顺序。
- 管理员身份、Origin 和 CSRF/同源保护继续生效。

### 批量同意

- 多条草稿分别按各自的 `project`、`knowledge`、`runbook`、`incident` 或 `reject` 推荐处理。
- 客户端不能覆盖模型推荐分类。
- 缺少推荐、缓存失效或项目绑定无效时，仅该项失败并保留。
- 一个项目门禁失败后，后续项目继续执行。
- 成功项记录最终 `review_category`，最终页面不保留 `review_recommendation`。

### 批量拒绝

- 不要求模型推荐。
- 每项先写审核记录，再软删除。
- 审核记录失败时不删除该草稿。
- 部分失败不回滚成功项。

### 界面与回归

- 列表存在行复选框、当前页全选、已选数量以及且仅有两个批量动作按钮。
- 未选择时按钮禁用，执行中不能重复提交。
- 页面不出现批量分类下拉框、预检、目标 slug、门禁码或确认短语。
- 完成后成功项消失，失败项保留并显示固定中文原因。
- 现有单条审核仍可修改分类并提交。
- 浏览器输出和服务端日志均不泄露凭据、原始异常或未脱敏正文。
- 现有 Basic Auth、writer attestation、review core、SPA fallback 和匿名 MCP 回归测试继续通过。

## 不在本次范围

- 跨页全选或“选择全部 inbox”。
- 为批量操作提供统一分类选择。
- 异步任务队列、进度轮询或后台重试。
- 批量入口即时调用模型生成缺失推荐。
- 修改草稿正文。
- 删除旧审核兼容 API。

## 验收标准

- 审核者可勾选当前页多条草稿，并且只看到“同意”和“拒绝并删除”两个批量决定。
- “同意”逐条采用最新草稿对应的有效模型推荐，不允许浏览器指定分类。
- “拒绝并删除”无需模型推荐，逐条先审计后软删除。
- 单项失败不影响其他项目；失败项仍在 inbox，成功项不回滚。
- 批量接口和页面继续满足管理员认证、同源、来源证明、脱敏和写入顺序约束。
- 单条分类审核行为保持不变。
