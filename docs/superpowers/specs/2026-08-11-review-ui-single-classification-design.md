# GBrain 单一分类经验审核设计

## 目标

审核者打开一条 inbox 草稿后，只完成一个决定：确认最终分类。页面先展示模型建议，审核者可以修改下拉框，然后点击一次确认按钮。服务端继续执行项目绑定、内容安全、重复检查、写入验证和审计记录，但不把这些内部步骤暴露成审核流程。

## 已确认事实

- 当前 `/admin/review` 流程包含详情、目标选择、预检和确认等多个页面。
- 当前详情页的“建议下一步”来自 `detailSuggestedNext` 的确定性判断。审核服务没有调用聊天模型生成建议。
- 采集 Agent 已经为新草稿填写 `type`、`project_binding`、`project_id`、适用场景和不适用场景。
- `planReview` 和 `applyReviewPlan` 已经集中实现项目边界、敏感内容、重复目标、写入、检索验证和审核记录。
- 现有管理员会话、同源检查和 writer 身份校验必须保留。

## 设计选择

### 采用方案：单条专注审核

页面左侧展示经验内容，右侧展示模型建议和分类控件。审核者一次只处理一条草稿。

备选方案是列表内联审核。它适合快速批量处理，但摘要空间不足，审核者更容易忽略适用条件和证据。用户已选择单条专注审核。

### 推荐来源：采集时优先，旧草稿回退

新草稿由采集 Agent 写入结构化推荐。审核服务先校验并展示该推荐，不重复调用模型。

旧草稿缺少结构化推荐时，审核服务通过现有模型网关生成一次推荐。第一版使用有界进程内缓存，键由 `source_id`、slug 和内容哈希组成。服务重启或缓存淘汰后，旧草稿可能再次调用模型。该限制换取零数据库迁移和较小维护面。

## 用户界面

详情页采用项目现有深色设计系统，正文区域最大宽度遵循 `DESIGN.md`。

页面包含：

1. 中文经验摘要。
2. 适用场景、不适用场景和验证状态。
3. 可展开的脱敏正文预览。
4. 模型推荐分类、中文使用场景和推荐理由。
5. 一个分类下拉框。
6. 一个确认按钮。

分类下拉框只有以下选项：

- `project`：项目经验
- `knowledge`：通用知识
- `runbook`：操作手册
- `incident`：故障经验
- `reject`：拒绝并删除

按钮默认显示“确认分类”。选择 `reject` 后显示“确认并删除”。页面不显示目标 slug、目标搜索、合并、补证据、预检、门禁码、确认短语、修复记录或清理残留。

## 结构化推荐契约

采集 Agent 写入的新草稿必须在 frontmatter 中提供：

```yaml
review_recommendation:
  category: project
  scenario: 设计或修改当前项目的经验审核流程。
  reason: 这条规则只约束当前项目，不适合作为跨项目知识。
  generated_by: model
```

审核服务把该字段视为界面建议，不把它视为写入授权。服务端执行以下校验：

- `category` 必须属于五项分类枚举。
- `scenario` 和 `reason` 必须是非空文本，各自最多 500 个字符。
- `generated_by` 必须为 `model`。
- `project` 分类要求草稿携带有效的 bound `project_id`。
- 所有动态文本继续通过浏览器安全脱敏和 HTML 转义。

推荐字段无效时，服务端按旧草稿处理，不显示伪造的模型结论。

## 组件边界

### `review/recommendation.ts`

纯逻辑模块，负责推荐契约解析、分类枚举、分类标签、缓存键和模型 JSON 结果校验。该模块不访问 Express、数据库或文件系统。

### `ReviewRecommendationProvider`

异步接口，输入浏览器安全的草稿投影，输出分类、场景和理由。默认实现复用项目现有聊天模型网关。`mountReviewRoutes` 接受可注入实现，测试不调用外部模型。

### `review/classification.ts`

把最终分类转换成现有 `ReviewAction`：

- `project` 生成项目命名空间目标并执行 `keep`。
- `knowledge`、`runbook`、`incident` 生成对应目标；项目绑定草稿使用 `promote`，其他草稿使用 `keep`。
- `reject` 生成 `reject`，服务端写入固定审计说明并软删除草稿。

该模块生成目标 slug 和内部动作。浏览器不提交目标 slug、action kind 或确认短语。

### 审核路由

详情页调用推荐解析器。有效的采集推荐直接随 HTML 返回。旧草稿不在 GET 请求中调用模型，因为浏览器预取和重复刷新可能产生意外费用。

旧草稿加载后，页面自动向同源保护的推荐入口提交 source slug。该 POST 入口查询最多 256 项的进程内缓存，缓存未命中时才调用 provider。整个过程不要求审核者点击额外按钮。

新增一个同源保护的分类确认入口。请求只接受：

```json
{
  "sourceSlug": "inbox/example",
  "category": "project"
}
```

服务端重新读取草稿，生成内部 action，重新运行全部门禁，再执行计划。客户端无法指定目标 slug、目标类型、human confirmation、writer 凭据或审核说明。请求出现未声明字段时返回 400。

旧的 plan/confirm API 暂时保留兼容性，但默认 HTML 页面不再链接这些入口。后续删除旧 API 需要单独的兼容性评估。

## 数据流

1. 采集 Agent 生成草稿正文和 `review_recommendation`。
2. `put_page` 保存草稿；现有项目身份校验保持不变。
3. 审核者打开详情页。
4. 服务端校验采集推荐。缺失或无效时，页面通过同源 POST 请求查询缓存，再按需调用模型。
5. 页面展示中文场景、理由和预选分类。
6. 审核者提交最终分类。
7. 服务端根据最新草稿重新构建 action 和目标，运行 `planReview`。
8. 门禁通过后，服务端通过已校验的 writer 会话执行 `applyReviewPlan`。
9. 成功后显示中文回执并提供下一条草稿入口。

## 错误处理

- 模型未配置、超时或返回非法 JSON：页面显示“暂时无法生成模型建议”，禁用确认按钮。系统不回退到旧多步骤流程，也不把确定性推断标成模型建议。
- 分类值未知：返回 400，并保持草稿不变。
- 项目分类缺少有效项目 ID：显示“该草稿未绑定项目，无法归为项目经验”。
- 内容安全、证据或重复门禁失败：在当前页面显示一条中文原因，保持草稿不变。页面不显示门禁码和内部计划。
- writer 身份或写入验证失败：返回固定浏览器安全错误，保持草稿不变。
- `reject` 成功：软删除草稿并写入审核记录。失败时保持草稿可见。

## 安全约束

- 所有读取和写入入口继续使用 `requireAdmin`。
- 分类确认继续执行严格同源检查。
- 浏览器只提交 source slug 和分类枚举。
- 服务端忽略或拒绝额外的目标、action、writer 和确认字段。
- 推荐文本进入 HTML 前执行脱敏和转义。
- 模型提示只使用浏览器安全投影，不发送凭据、原始认证文件或密集日志。
- 现有 writer MCP URL 校验、source attestation 和 review core 门禁保持不变。

## 测试

### 纯逻辑测试

- 五项分类解析与中文标签。
- 结构化采集推荐的有效、缺失和非法输入。
- project 分类的 project ID 约束。
- 分类到 `ReviewAction` 的映射和目标 slug 生成。
- 模型 JSON 的枚举、长度和未知字段处理。
- 缓存键随内容哈希变化而失效。

### 路由测试

- 详情页只显示一个下拉框和一个确认按钮。
- 页面不包含预检、门禁码、目标 slug、确认短语和审核说明表单。
- 有效采集推荐不会调用 provider。
- 详情 GET 不调用 provider。
- 旧草稿的同源推荐 POST 只在缓存未命中时调用 provider。
- 模型失败时禁用提交，不伪造建议。
- POST 只接受 source slug 和分类；额外敏感字段被拒绝。
- project、knowledge、runbook、incident 和 reject 分别执行正确内部计划。
- 同源、管理员身份和 writer source 校验继续生效。
- 门禁失败保留草稿，拒绝成功软删除草稿。

### 回归测试

- 现有 review core 测试继续通过。
- 浏览器安全投影和错误响应不泄露 token、secret、bearer 或原始异常。
- 审核历史继续记录来源、最终分类对应动作、目标和状态。

## 文档更新

`docs/mcp/WEB_UI_REVIEW.md` 改为单一分类流程。采集 Agent 规则增加结构化推荐字段说明。旧 plan/confirm API 标记为兼容接口，不再描述为默认人工流程。

## 不在本次范围

- 批量审核。
- 合并草稿的默认 UI。
- 持久化模型推荐缓存。
- 删除旧 plan/confirm API。
- 修改 review core 的安全门禁语义。
- 自动晋升或绕过人工确认。

## 验收标准

- 审核者只看见一个分类下拉框和一个确认按钮。
- 每条可提交草稿都有真实模型来源的建议。
- 新草稿优先使用采集时建议，不产生重复模型调用。
- 旧草稿推荐失败时不能提交，也不会显示伪造建议。
- 用户一次确认后，服务端完成目标生成、门禁、写入、验证和审计。
- 选择“拒绝并删除”使用同一个分类提交入口，并执行可恢复的软删除。
