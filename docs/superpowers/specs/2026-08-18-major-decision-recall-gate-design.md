# GBrain 重大决策与失败召回门禁设计

## 目标

GBrain 自动 Recall 只服务于两类时机：执行高影响决策之前，以及当前方案发生非预期执行错误之后。普通修改、小功能、常规修复、一般排障和成功的工具调用不触发 Recall。

本设计只修改 GBrain 源码及其生成的客户端资产，不修改 Codex CLI 或 OpenCode 的原生逻辑。自动 Closeout 保持关闭，Recall 仍然只读，不授权写入经验。

## 当前问题

当前客户端使用宽泛的 `NONTRIVIAL_RE` 判断是否自动召回。`修改`、`实现`、`修复`、`部署`、`诊断`、`总结` 及其英文对应词都会命中，因此大量不需要历史经验的小任务在开始前派生 Recall Worker。

仅删除几个关键词不能稳定解决问题。重大决策需要同时具备“正在做选择或改变策略”和“影响范围较高”两个信号；执行失败则发生在任务开始之后，需要独立于决策门禁处理。

## 方案选择

采用确定性的双门槛状态机：

1. 用户提交 prompt 时，GBrain 只判断是否存在高影响决策意图。
2. 工具执行结束时，GBrain 只判断是否出现非预期失败。

不采用每条消息都调用模型分类的方案，因为它会给所有请求增加延迟、成本和新的误判来源。不采用完全手动 Recall，因为用户要求当前方案报错后仍能自动利用历史故障经验。

## 决策前召回门槛

GBrain 将决策意图与高影响领域拆成两个独立信号，两个信号同时成立才自动召回。

决策意图包括：

- 选择、选型、比较并决定方案；
- 改变架构、策略、边界或长期规则；
- 决定是否执行不可逆或高成本操作。

高影响领域包括：

- 系统架构、技术栈、数据库或核心协议；
- 认证、授权、安全、隐私和密钥边界；
- 生产环境拓扑、流量入口和关键基础设施；
- 数据迁移、批量删除、不可逆转换和恢复策略；
- 全局规则、项目规则和影响后续任务的长期约束。

用户明确提出“召回经验”“查历史经验”或同义要求时，无需同时满足以上两个信号，直接触发只读 Recall。

以下内容单独出现时不得触发：

- 修改、实现、开发、修复或重构；
- 小功能、样式、文案、测试或常规配置；
- 常规部署、重启、状态检查或日志查看；
- 普通诊断、排障、解释、总结或代码审查；
- 仅提到架构、安全、生产等名词，但没有选择或改变决策的请求。

## 失败后召回门槛

Codex 客户端重新安装一个 GBrain 管理的 `PostToolUse` handler。该 handler 只把工具结果交给本地 GBrain 守卫判断；成功结果立即返回空对象，不签发 token，也不注入上下文。

下列信号属于非预期失败：

- 命令返回非零退出码，且不属于预期测试或否定探测；
- 工具明确返回 `isError`、异常状态或结构化错误；
- 已选择的执行方案因环境、依赖、权限或实现错误无法继续。

下列信号不触发失败 Recall：

- TDD 中明确预期的 RED 测试；
- 用于检查“不存在”“未监听”“未匹配”的否定探测；
- 用户取消、权限审批拒绝或主动中断；
- 守卫能从固定错误类型识别的 shell 解析错误、参数缺失或用户输入路径不存在；
- 成功调用、只读调用数量或子 Agent 数量。

每个父任务回合最多自动触发一次失败 Recall；父任务回合由同一 `session_id` 和 `turn_id` 标识。守卫只保存布尔状态、时间、哈希化工具类型和错误类别，不保存原始命令、错误正文、工具输出或 transcript。后续相同或不同错误都不会在同一回合再次派生 Worker；新的用户回合重新获得一次失败召回额度。

主 Agent 派发失败 Recall Worker 时，只传递脱敏后的操作类别、稳定错误码或错误类别，以及判断适用性所需的环境类别。原始命令、完整 stderr、路径、地址和凭据不得进入 Worker prompt。

如果回合开始时已经完成一次决策 Recall，后续首次非预期失败仍可签发新的 Recall token。失败 Recall 与决策 Recall 使用独立轮次状态，避免复用或覆盖已经消费的 token。

## Codex 数据流

1. `UserPromptSubmit` 把 prompt 交给 GBrain 守卫。
2. 守卫仅在“决策意图 + 高影响领域”或用户明确要求时签发决策 Recall token。
3. `PostToolUse` 把工具结果交给同一守卫。
4. 守卫过滤成功和预期失败；首次非预期失败签发失败 Recall token。
5. Recall Worker 只读搜索并提交最小 receipt。
6. `Stop` 不注册 GBrain handler，不执行 Closeout，也不阻止最终答复。

安装器每次运行都会移除旧版 GBrain 管理的 Hook，再写入 `UserPromptSubmit` 和失败观察型 `PostToolUse`。非 GBrain Hook 保持不变。

## OpenCode 数据流

OpenCode 的 `chat.message` 使用相同的决策门槛。工具成功不进入 GBrain 状态机；工具失败或错误事件进入失败门槛。

失败上下文暂存在内存中，并通过下一次 `experimental.chat.system.transform` 交给当前模型步骤。插件不恢复 `session.idle`、`promptAsync` 或 Stop 续跑。完成注入后立即删除暂存上下文，保证同一失败不会重复出现。

## 规则与文档

安装后的 GBrain 客户端规则改为：

- 重大决策前自动只读 Recall；
- 当前方案发生首次非预期执行错误后允许一次故障 Recall；
- 普通任务不自动 Recall；
- 自动 Closeout 保持关闭；
- 只有用户明确要求持久化时才使用 `gbrain-capture`。

安装器帮助、JSON 模式说明、部署文档和 `KEY_FILES.md` 使用相同术语，避免把新门槛继续描述为“所有非平凡任务”。

## 错误处理

- 守卫解析工具结果失败时 fail-open，不触发 Recall。
- 状态目录不可安全访问时返回固定警告，不读取或跟随不可信符号链接。
- Recall token 无效、过期或重放时保持现有拒绝行为。
- OpenCode 子进程超时或返回无效 JSON 时只返回固定警告，不启动 idle 续跑。
- 失败观察入口不得把原始错误信息写入状态文件或 Recall envelope。

## 验证

新增或更新测试覆盖：

1. “修复一个按钮样式”“实现一个普通接口”“部署当前构建”不触发 Recall。
2. “在两种数据库之间选型并决定生产架构”触发决策 Recall。
3. “修改认证与权限模型”只有在包含选择或边界改变意图时触发。
4. 用户明确要求召回时直接触发。
5. 成功的 `PostToolUse` 返回空对象。
6. 首次非预期失败触发一次故障 Recall，后续失败不重复触发。
7. 预期 RED 测试、否定探测和用户取消不触发。
8. 完成决策 Recall 后，首次非预期失败仍能获得独立 token。
9. Codex 安装配置包含 GBrain 管理的 `UserPromptSubmit` 和 `PostToolUse`，不包含 `Stop`。
10. 安装修复保留非 GBrain 的 `PostToolUse` 和 `Stop` handler。
11. OpenCode 只在失败时暂存并注入 Recall 上下文，不注册 idle 续跑。
12. 状态文件不包含 prompt、命令或错误正文。

完成专项测试后运行 `bun run verify` 和仓库默认测试入口。更新生成文档后安装本机客户端，并回读两端配置验证触发路径。

## 成功标准

- 普通小需求和成功执行不再出现 Recall Worker。
- 重大决策在执行前召回一次。
- 当前方案首次出现非预期错误后召回一次。
- 同一回合不会形成召回风暴。
- Stop Closeout、自动总结和自动经验写入保持关闭。
